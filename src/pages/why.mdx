<p class="eyebrow">Why tabnas</p>



I wanted to build a general parser that could be extended by
plugins. Say you have plain old JSON, but the values could be expressions, not just
fixed values. Well, originally I wanted to build a better JSON parser
(who doesn't) that could handle a more relaxed syntax. I'm lazy and
don't want to quote everything.


How do you make a parser that can be extended? Most parsers take a
grammar and turn it into generated (and yucky) code. Or you write
recursive descent by hand. I always believed you had to have some
serious computer science mechanism, like
[ANTLR](https://www.antlr.org) (which is pretty cool). Then I read a
great article about how [most real language parsers are written by
hand](https://notes.eatonphil.com/parser-generators-vs-handwritten-parsers-survey-2021.html). No,
for real.

The original version of my easy-going JSON parser was
[jsonic](http://github.com/jsonicjs/jsonic), built with
[pegjs](https://github.com/pegjs/pegjs) (also cool).  So during COVID,
with a failing startup (you know the way you are advised to never
start a land war in Asia? Well, never do an event management
startup. Same thing), a little time on my hands, and permission from
some random blog post, I decided, feck it, I'll just rewrite my JSON
parser by hand!

# A grammar is a table of translations.

<p class="lede">
  Parsing is a solved problem — and yet every team solves it again, badly,
  once per language and once per runtime. tabnas exists to stop that.
</p>

## The problem

Reach for a parser today and you pick a compromise:

- **Hand-rolled parsers** are fast to start and slow to trust. Edge cases
  pile up, the code becomes the spec, and no two are alike.
- **Regex** works until the language nests — then it quietly gives wrong
  answers instead of errors.
- **Parser generators** (ANTLR, tree-sitter, PEG tools) give you a grammar,
  but also a build step, generated code to keep in sync, and a runtime that
  usually only speaks one language well.

And when you need the _same_ language in more than one place — a Node service
and a Go binary, an editor plugin and a CLI — you write it twice and watch the
two drift apart.

## The tabnas approach

<CardGrid>
  <Card title="The grammar is the parser">
    No generated code to fall out of sync. You install a grammar and it
    parses — or you compile one from ABNF at runtime. Inspect it live,
    render it back to ABNF, draw it as a diagram.
  </Card>
  <Card title="One grammar, two runtimes">
    TypeScript is canonical; Go tracks it exactly, verified against the
    same fixtures. Ship identical language support to Node and Go without
    maintaining two parsers.
  </Card>
  <Card title="A uniform tree">
    Every parse yields the same shape — `{ rule, src, kids }` — so walkers,
    actions, and tooling written once work for every language you define.
  </Card>
</CardGrid>

<p class="fine">
  tabnas isn't the fastest parser for every workload, and it isn't trying to
  be a full compiler toolchain. It's the shortest path from "I have a
  grammar" to "I have a parser I can trust, everywhere I run."
</p>

## The name

**tabnas** is Irish — _{SITE_MOTTO}_, "a table of translations." That's
exactly what a grammar is: a table that turns one form into another. The
emblem is that table, illuminated.
